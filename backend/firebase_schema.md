# Firebase (NoSQL) Database Redesign

When migrating from PostgreSQL to Firebase Cloud Firestore (NoSQL), the key difference is that NoSQL databases optimize for **fast reads** by denormalizing data and reducing the need for complex joins. 

Here is the proposed redesigned schema for your College Event Management Platform:

## 1. `users` Collection
Instead of auto-incrementing IDs, we use the `uid` provided by Firebase Authentication as the document ID.
*   **Document ID:** `userId` (Firebase Auth UID)
*   **Fields:**
    *   `name` (string)
    *   `email` (string)
    *   `college` (string)
    *   `phone` (string)
    *   `role` (string) - *'student' or 'admin'*
    *   `createdAt` (timestamp)
    *   *(Optional Denormalization)* `registeredEventIds` (array of strings) - *Keeps track of events the user has registered for.*

*(Note: Passwords are removed from the database as Firebase Authentication securely handles credentials).*

## 2. `events` Collection
*   **Document ID:** Auto-generated by Firestore (`eventId`)
*   **Fields:**
    *   `title` (string)
    *   `description` (string)
    *   `eventDate` (timestamp or string YYYY-MM-DD)
    *   `eventTime` (string)
    *   `deadline` (timestamp)
    *   `venue` (string)
    *   `location` (string)
    *   `coordinatorName` (string)
    *   `contactInfo` (string)
    *   `imageUrl` (string)
    *   `whatsappLink` (string)
    *   `eventType` (string) - *'individual' or 'team'*
    *   `maxTeamSize` (number)
    *   `minTeamSize` (number)
    *   `maxParticipants` (number)
    *   `createdBy` (string) - *Reference to `userId`*
    *   `createdAt` (timestamp)
    *   *(Optional Denormalization)* `registeredCount` (number) - *Tracks total number of registrations to easily enforce `maxParticipants`.*

## 3. `teams` Collection
In SQL, you had `teams` and `team_members`. In Firestore, since a team won't have millions of members, it's more efficient to embed the members as an array within the team document.
*   **Document ID:** Auto-generated by Firestore (`teamId`)
*   **Fields:**
    *   `name` (string)
    *   `teamCode` (string) - *Must be validated for uniqueness via backend logic or Firestore Rules*
    *   `leaderId` (string) - *Reference to `userId`*
    *   `eventId` (string) - *Reference to `eventId`*
    *   `createdAt` (timestamp)
    *   `members` (array of strings) - *Array of `userId`s belonging to this team. This replaces the `team_members` SQL table.*

## 4. `registrations` Collection
While you can track registrations by just adding the `eventId` to the user's document, keeping a `registrations` collection helps with querying "who registered for event X" and tracking when they registered.
*   **Document ID:** Combination of `userId_eventId` (to easily prevent duplicate registrations)
*   **Fields:**
    *   `userId` (string)
    *   `eventId` (string)
    *   `teamId` (string, optional) - *If it's a team event*
    *   `registeredAt` (timestamp)

---

## Why this structure?
1.  **No `team_members` table:** Instead of joining `teams` and `team_members`, we just store member IDs in a `members` array inside the `team` document. This makes loading a team and its members a single read operation.
2.  **No Passwords:** We assume you will migrate to **Firebase Authentication**, meaning you won't store hashed passwords in your database anymore.
3.  **Unique Registrations:** By setting the Document ID of a registration to `${userId}_${eventId}`, you automatically enforce uniqueness without needing to query first.
